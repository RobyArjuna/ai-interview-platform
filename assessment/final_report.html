1. Overview & Key Context

I audited the AI Interview Platform repository to evaluate its fullstack architecture (api/ Rails backend & web/ React frontend).

During my audit, I identified a critical flaw in how unassessed skills were handled during candidate portfolio generation, along with compliance gaps regarding Indonesia's Personal Data Protection Law (UU PDP).

Primary Problem Addressed (P0 Bug)

When a candidate completed an interview, any skill configured in AssessmentSkill that wasn't probed during the session was automatically assigned a Level 1 score by Portfolios::Generator#save_skills.

Converting nil to Level 1 using .to_i.clamp(1, 5) penalized candidates with false-negative scores for skills they were never asked about. Furthermore, when running Fit/Gap analysis against job vacancies, evaluating nil candidate ratings caused FitGap::Engine to crash with a NilClass subtraction error (NoMethodError: undefined method '-' for nil:NilClass).

2. Technical Fixes & Engineering Decisions

Backend Changes (api/)

  • Unassessed Skill Model & Migration: Created database migration 20260505000003_allow_null_ai_level_in_portfolio_skills.rb to drop NOT NULL on portfolio_skills.ai_level and update Postgres check constraints to allow NULL. Added 'not_assessed' to confidence_level enum.
  • UU PDP Data Privacy Redaction: Built PdpSanitizer (api/app/lib/pdp_sanitizer.rb) to redact 16-digit NIK numbers, Indonesian phone numbers (+62 / 08xx), and emails from candidate transcript turns before logging or calling external Gemini LLM APIs.
  • Resilient AI Response Handling: Added markdown codeblock stripping (```json ... ```) and safe error trapping in Portfolios::Generator#save_skills to prevent job worker crashes on raw LLM output formats.

Frontend Changes (web/)

  • Neutral Unassessed UI Badge: Updated LevelBadge.tsx and ConfidenceIndicator.tsx to render a neutral N/A - Unassessed badge and Status: NOT ASSESSED indicator when ai_level is null.
  • Fit/Gap Component Safeguard: Handled missing candidate levels in OverridePanel.tsx and FitGap UI components so recruiters see "Not assessed" instead of NaN or UI breakage.

3. Trade-off Analysis: Single PR vs Micro-PRs

I chose to deliver these changes in a Single Comprehensive Pull Request (Option A).

Rationale: The changes in api/ (schema migration, service logic) and web/ (UI components, TypeScript types) form a single atomic fullstack feature slice. Splitting them into separate micro-PRs would create transient states where backend DB schema support for nil levels exists without corresponding frontend rendering support.
